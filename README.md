# etu-forms (backend)

Конструктор форм (API): создание форм вручную или с помощью ИИ помощника, публикация,
приём ответов от неавторизованных пользователей, фильтрация ответов и выгрузка
в .xlsx фоновой задачей.

REST API, всё общение по JSON, авторизация через Bearer Token.

## Стек

Node.js 24, TypeScript (strict), Express 5, PostgreSQL (pg) с чистым SQL без ORM,
миграции dbmate, очереди BullMQ + Redis, Zod, ESLint + Prettier.

## Быстрый старт

```bash
cp .env.example .env      # проверить DB_*, REDIS_*, AI_API_KEY
docker compose up -d      # postgres + redis, в DATABASE_URL дописать ?sslmode=disable
npm ci
npm run db:up             # миграции
npm run db:seed           # наполнение бд тестовыми данными (необязательно)
npm run dev               # запуск приложения
npm run worker            # обработчик фоновых задач (отдельным процессом)
```

Проверка состояния приложения - `GET /health`, API находится в `/api`.
Экспорт ответов работает только когда запущен обработчик фоновых задач.

## Структура

```
src/
  main.ts        точка входа приложения
  worker.ts      точка входа обработчика фоновых задач
  seed.ts        точка входа наполнения бд
  app/           сборка приложения: контейнер зависимостей, express, сервер
  config/        конфиги приложения
  core/          инфраструктура: базовые контроллеры, репозитории, политики,
                 сервисы для слоя БД, слой для Redis, файловое хранилище, базовое DTO
  modules/       фичи (см. ниже)
  routes/        группы маршрутов (например, /api): собирает роутеры всех модулей в
                 одно дерево адресов
  seed/          сценарии наполнения базы
  shared/        мелкие общие вещи: ошибки, http-утилиты, логгер, безопасность

db/              миграции dbmate и снимок схемы
docs/            документация API
prompts/         тексты промптов для ИИ-конструктора
scripts/         вспомогательные скрипты (создание миграции)
storage/         файлы приложения: выгрузки и временные файлы
```

### Структура модуля

У всех модулей она одинаковая, отличается только набор необязательных файлов:

```
src/modules/<module>/
  index.ts             публичный контракт: то, что могут импортировать другие модули (есть не у всех)
  <e>.module.ts        сборка модуля: создаёт репозиторий, сервис, политику, контроллер
  <e>.types.ts         общее описание сущности
  <e>.domain.ts        чистые правила и вычисляемые значения без знания о БД и I/O
  <e>.service.ts       бизнес-логика
  <e>.policy.ts        политика доступа к экземплярам
  api/
    <e>.routes.ts      адреса модуля и их middleware
    <e>.controller.ts  HTTP контроллер: разобрать запрос, вызвать сервис, вернуть ответ
    <e>.dto.ts         zod-схемы запроса и типы контракта
    <e>.mapper.ts      перевод сущности в JSON для клиента
  db/
    <e>.repository.ts  SQL
    <e>.metadata.ts    описание БД вида сущности (самой таблицы)
    <e>.scope.ts       обязательные условия выборки (например, только свои формы)
    <e>.filter.ts      необязательные условия выборки (фильтры)
    <e>.seeder.ts      наполнение тестовыми данными
  test/                юнит-тесты модуля
```

Что откуда можно импортировать:

| Файл            | Кто импортирует                                                                                   |
| --------------- | ------------------------------------------------------------------------------------------------- |
| `index.ts`      | любой другой модуль                                                                               |
| `<e>.module.ts` | только сборка приложения (`app/`)                                                                 |
| всё остальное   | сам модуль, по относительным путям <br/> (например, `/db` не может зависеть от `/api` и наоборот) |

Это проверяет ESLint.

## Как проходит запрос

Сверху вниз - путь обычного запроса, снизу вверх - путь ответа:

```
   HTTP-запрос
        │
   app/app.ts               cors, разбор JSON, общий лимит запросов, /health
        │
   routes/api.routes.ts     /api/forms → модуль form, /api/jobs → модуль job
        │
   api/<e>.routes.ts        авторизация и проверка тела запроса по dto
        │
   api/<e>.controller.ts    достаёт данные из запроса, спрашивает разрешение
        │                   у policy, собирает scope, filter и pagination
        │
   <e>.service.ts           правила и порядок действий (бизнес-логика)
        │
   db/<e>.repository.ts     SQL
        │
   PostgreSQL
        │
        ▼   обратно поднимается сущность
   api/<e>.mapper.ts        сущность → JSON, каким его увидит клиент
        │
   HTTP-ответ
```

Фоновые задачи (долгие операции) идут короче: контроллер только ставит задачу
в очередь и сразу отвечает клиенту её идентификатором. Дальше её забирает
отдельный процесс `worker.ts`, а клиент опрашивает `/api/jobs/:id`,
пока не увидит результат. Так устроен экспорт ответов в .xlsx, например.

### Разработка

| Пример задачи                         | Файл(-ы)                                          |
| ------------------------------------- | ------------------------------------------------- |
| добавить или убрать эндпойнт          | `api/<e>.routes.ts`, `api/<e>.controller.ts`      |
| поменять формат или валидацию запроса | `api/<e>.dto.ts`                                  |
| дополнить ответ клиенту               | `api/<e>.mapper.ts`, `api/<e>.domain.ts`          |
| изменения уровня доступа              | `<e>.policy.ts`, `db/<e>.scope.ts`                |
| бизнес-правило, порядок действий      | `<e>.service.ts`                                  |
| запрос к базе                         | `db/<e>.repository.ts`                            |
| новая колонка в БД                    | миграция в `db/migrations` + `db/<e>.metadata.ts` |
| добавить фильтр                       | `db/<e>.filter.ts`                                |
| «видно только своё»                   | `db/<e>.scope.ts`                                 |

Файлы в `core/` и `shared/` - общие для всех модулей. Правка там чинит или
ломает сразу всё, так что менять их стоит осознанно, а не ради одного случая.
